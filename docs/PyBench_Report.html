01 · Project overview

Learn Python by running it

Notes on Python usually show a program and its output side by side. PyBench lets you change the program and see the new output straight away. Every page is a short explanation followed by working code. Next to the code are small tools that show what Python is doing: an expression stepper for the order of operations, a loop tracer, a slice visualizer, a recursion tree, a regex tester and a file explorer. The tools are written in Python too, and the page calls them.

What makes it more than a set of notes

  • It is real Python. The site runs CPython 3.12 compiled to WebAssembly (Pyodide). The .py files in the repository are copied into the browser's Python when it starts, so the practicals and tools run exactly the code that is in the project.
  • The same code runs on a computer. python -m pybench opens a menu with the unit demos, the practicals and MailGuard. python -m unittest runs 46 tests, and everything uses only the standard library.
  • The tools explain Python with Python. The expression stepper parses your expression with the ast module. The loop tracer records every executed line with sys.settrace. The recursion tree is built by a recursive function.
  • A small real project. MailGuard grew out of practical 14. It reads mails from files, applies six rule classes and explains its score, and it has a Kaggle / Jupyter notebook version with tables and charts.

02 · How it's built

Python in the browser

The site is plain HTML, CSS and JavaScript modules with no framework and no build step, hosted on GitHub Pages. Python runs in a Web Worker, so a long or endless loop never freezes the page. The page sends code to the worker, and the worker sends back what it printed.

11 · MailGuard

A phishing mail analyser

Practical 14 asks for the most common words in ten phishing mails. Counting words made it obvious that phishing mails share patterns: they rush you, they ask for an OTP or a card number, the sender's domain doesn't match the brand, and the links hide where they go. MailGuard turns each pattern into a rule class and adds the points up into a score with reasons. CO1–CO6

How it uses the syllabus

PartWhat it doesUnit
MailSplits headers from body at the first blank line, reads the headers with a multiline regex, and gives sender_domain, urls and words(); Mail.from_file() is a classmethod that reads a fileIII, V, VI
Rule + 6 subclassesUrgencyRule, CredentialRule, LinkRule, SenderRule, MoneyRule and AttachmentRule each override check(mail); MailGuard calls check() without knowing which rule it has (polymorphism)V
Finding, ReportA finding is one reason with points. A report adds them up (max 100), has a verdict property and __lt__, so a list of reports can be sortedIII, V
MailGuardKeeps its rules in a name-mangled __rules list (data hiding). analyse_folder() lists a directory and skips unreadable files with try / exceptV, VI
save() / load()Pickle the reports to a binary file; a missing file gives an empty list instead of a crashVI
common_words()Counter of words minus stop words, which is practical 14III

The notebook version

notebooks/mailguard_analysis.ipynb runs the same package in a Jupyter / Kaggle notebook. In Kaggle, turn Internet on and the first cell clones the repository. It puts the reports into pandas tables, compares the phishing and normal sets, counts points per rule, extracts every link with a regex, adds a seventh rule as a subclass and saves the reports with pickle. The charts below are the notebook's real output. I executed it with pandas and matplotlib inside Pyodide, because neither is installed on my laptop.

The sample is small and made by me (10 phishing and 4 normal mails), so the perfect result here does not mean MailGuard would be perfect on real inboxes. The next step would be a larger public dataset and learning the rule weights from it instead of choosing them by hand.

py-worker.js · lines 18–45def _pb_run(code, stdin, filename, as_file):
    buf = io.StringIO()

    def fake_input(prompt=''):

        value = lines.pop(0)
        buf.write(value + '\\n')

    sys.stdout = sys.stderr = buf

    error = None

        if as_file:
            runpy.run_path(filename, run_name='__main__')
        else:
            exec(compile(code, filename, 'exec'), {'__name__': '__main__'})
    except SystemExit:
        pass
    except BaseException as err:

    finally:

Every run goes through this Python function inside the worker. It points sys.stdout and sys.stderr at one StringIO, so prints and errors appear in the order they happened.

input() is replaced with fake_input, which writes the prompt, takes the next line from the Input box and echoes it, the way a terminal shows what you typed. If the program asks for more input than was given it raises EOFError with a clear message instead of hanging.

Practicals run as files with runpy.run_path(..., run_name='__main__'), so their if __name__ == "__main__" block runs exactly as with python p01.py. Tracebacks are trimmed so they show only your code, not the runner.

py.js · lines 41–52function post(type, payload, timeout) {

Python in a worker can't be interrupted unless the server sends special headers, which GitHub Pages doesn't. So each request gets a timer. If it fires, the worker is terminated and a fresh one starts, and the cell shows a TimeoutError. The expression stepper

unit1_basics.py · lines 81–126def evaluation_steps(expression):
    """Evaluates an arithmetic expression one operator at a time, in the order
    Python does it (PEMDAS + left-to-right, ** right-to-left). Returns the steps."""
    tree = ast.parse(expression, mode="eval")
    steps = []

    def walk(node):
        if isinstance(node, ast.Constant):
            return node.value
        if isinstance(node, ast.BinOp):
            left = walk(node.left)
            right = walk(node.right)
            result = eval(f"{left!r} {OPS[type(node.op)]} {right!r}")
            steps.append(f"{left!r} {OPS[type(node.op)]} {right!r} = {result!r}")
            return result
        if isinstance(node, ast.UnaryOp):
            operand = walk(node.operand)
            result = eval(f"{OPS[type(node.op)]}{operand!r}")
            steps.append(f"{OPS[type(node.op)]}{operand!r} = {result!r}")
            return result
        if isinstance(node, ast.BoolOp):
            value = walk(node.values[0])
            word = OPS[type(node.op)]
            for nxt in node.values[1:]:
                if (word == "and" and not value) or (word == "or" and value):
                    steps.append(f"{value!r} {word} ... = {value!r} (short-circuit, right side never runs)")
                    return value
                right = walk(nxt)
                result = (value and right) if word == "and" else (value or right)
                steps.append(f"{value!r} {word} {right!r} = {result!r}")
                value = result
            return value
        if isinstance(node, ast.Compare):
            left = walk(node.left)
            result = True
            for op, comp in zip(node.ops, node.comparators):
                right = walk(comp)
                ok = eval(f"{left!r} {OPS[type(op)]} {right!r}")
                steps.append(f"{left!r} {OPS[type(op)]} {right!r} = {ok!r}")
                result = result and ok
                left = right
            return result
        raise ValueError("only numbers, operators and brackets please")

    result = walk(tree.body)
    return steps, result

ast.parse(..., mode="eval") turns the expression into a tree that already follows Python's precedence rules, so 2 + 3 * 4 becomes Add(2, Mult(3, 4)). Walking the tree depth first and recording each operator as it is evaluated gives the steps in the order Python really uses.

and / or are handled separately to show short-circuiting: when the left side already decides the answer, the right side is never walked, so 0 and 1 / 0 doesn't raise. Only literals and operators are accepted, so the tool can't be used to run other code.

The loop tracer

unit2_control.py · lines 188–213def trace(source, max_steps=200):
    """Runs a small program and records every line executed with the variables
    at that moment (and what was printed so far). The loop tracer on the site uses it."""
    steps = []
    code = compile(source, "<tracer>", "exec")
    printed = io.StringIO()

    def tracer(frame, event, arg):
        if frame.f_code.co_filename != "<tracer>":
            return tracer
        if event == "line":
            names = {k: v for k, v in frame.f_locals.items() if not k.startswith("__") and isinstance(v, (int, float, str, bool, list, tuple))}
            steps.append((frame.f_lineno, {k: repr(v) for k, v in names.items()}, printed.getvalue()))
            if len(steps) >= max_steps:
                raise RuntimeError(f"stopped after {max_steps} steps (infinite loop?)")
        return tracer

    scope = {"__builtins__": __builtins__}
    sys.settrace(tracer)
    try:
        with redirect_stdout(printed):
            exec(code, scope)
    finally:
        sys.settrace(None)
    steps.append((None, steps[-1][1] if steps else {}, printed.getvalue()))
    return steps

sys.settrace makes Python call tracer for events in every frame. For each "line" event in the traced program it stores the line number, a copy of the simple local variables and the output printed so far. That is a dry run on paper, done by Python itself.

A step limit stops infinite loops with a clear message, and the tracer is always removed in finally. The page then lets you move through the steps and highlights the variable that changed.

The recursion tree

unit4_functions.py · lines 120–137def call_tree(name, n):
    """Records the recursion tree of factorial / fib so the site can draw it.
    Each node is [label, result, children]."""
    def fact_node(k):
        if k <= 1:
            return [f"fact({k})", 1, []]
        child = fact_node(k - 1)
        return [f"fact({k})", k * child[1], [child]]

    def fib_node(k):
        if k < 2:
            return [f"fib({k})", k, []]
        a, b = fib_node(k - 1), fib_node(k - 2)
        return [f"fib({k})", a[1] + b[1], [a, b]]

    if name == "fib":
        return fib_node(min(n, 7))
    return fact_node(min(n, 10))

The tree is built by the same recursion it shows: each call returns [label, result, children]. The JavaScript only draws it. Leaves are placed left to right and each parent is centred over its children. n is capped so the fib tree stays readable (fib(7) already has 41 calls).

unit3_data.py · lines 137–158class SparseMatrix:
    """A matrix that stores only non-zero cells in a dict keyed by (row, col)."""

    def __init__(self, rows, cols):
        self.rows, self.cols = rows, cols
        self.cells = {}

    def __setitem__(self, pos, value):
        if value:
            self.cells[pos] = value
        else:
            self.cells.pop(pos, None)

    def __getitem__(self, pos):
        return self.cells.get(pos, 0)

    def dense(self):
        return [[self[r, c] for c in range(self.cols)] for r in range(self.rows)]

    def saving(self):
        total = self.rows * self.cols
        return f"{len(self.cells)} of {total} cells stored ({100 - 100 * len(self.cells) // total}% saved)"

__setitem__ and __getitem__ let the class be used like a matrix: m[2, 3] = 7. Only non-zero cells are kept in the dictionary; setting a cell to 0 removes it, and get(pos, 0) supplies the zeros.

mailguard.py · lines 100–119class LinkRule(Rule):
    name = "suspicious link"
    weight = 12
    SHORTENERS = ("bit.ly", "tinyurl.com", "t.co", "rb.gy", "cutt.ly", "is.gd")

    def check(self, mail):

            host = re.sub(r"^https?://", "", url).split("/")[0].lower()

            elif url.startswith("http://"):

            if host.count("-") >= 2 or re.search(r"(login|secure|verify|update|account)[\w-]*\.", host):
                findings.append(self.hit(f"domain made to look official ({host})", 10))
        return findings

LinkRule overrides check(). For each URL found with the shared URL pattern it takes the host and checks, in order: a bare IP address (20 points), a link shortener, an @ inside the URL (the browser ignores everything before it), or plain http. Separately it checks for hosts built to look official (login-, secure-, many hyphens).

Each problem becomes a Finding with a readable reason, so the score can always be explained.

What I learned

  • Python can explain itself. The ast module shows how an expression is grouped, and sys.settrace shows which line runs next. Building the stepper and the tracer taught me the order of operations and loops better than reading about them.
  • Aliasing is easy to get wrong. [[0] * 2] * 2 gives the same inner list twice. I hit it myself before I made the aliasing tab.
  • Stable sorting is useful. Sorting by name first and then by marks keeps ties in alphabetical order, which fixed a real bug in the sorting tool.
  • Inheritance pays off when things get added. Adding a new MailGuard rule is just a subclass with one method, and nothing else changes. That is what polymorphism is for.
  • Files and exceptions belong together. Almost every file operation needed a try / except somewhere: a missing file, an unreadable mail, a pickle that isn't there yet.
  • Regex is great for known formats and fragile for everything else. The scraper works on the sample shop page because I know its layout; a real site would need an HTML parser.
